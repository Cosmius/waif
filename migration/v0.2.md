# Reading v0.2 task artifacts

Task artifacts written for v0.2 may use forms that the current protocol no
longer describes. Read them as follows; the current protocol and templates
define the forms to write.

## Plan decisions

A plan decision that needed its own section used a separate `P-DD<number>`
family after the `- P-D<number>` decisions:

```markdown
- P-D1: Keep the parser line-oriented.

### P-DD1: Storage format
```

`P-DD<number>` decisions are plan decisions like `P-D<number>`, numbered in
their own series. References to `P-DD1` elsewhere in the task mean that
decision.

As a special treatment for ID migration, a migrated `P-DD<number>` becomes
`P-D<number + 100>`, and every reference to it changes with it: `P-DD1`
becomes `P-D101`. If the plan already uses such a `P-D` ID, ask the user how
to resolve the conflict.

## Plan-item coverage

A step plan wrote each plan-item coverage entry as a single item:

```markdown
- S3-PC2: P2 - partial - parser support for gap detection; checker
          diagnostics follow in a later step
```

The text before the first ` - ` is the covered plan item, the text before the
second is the coverage, `partial` or `complete`, and the rest describes what
the step covers.

## Step sections

A step plan listed its done conditions in `Done When`, with IDs
`S<n>-D<m>`, and described each concrete change, naming paths and
interfaces, in `Changes`. Sections followed this order: `Objective`,
`Plan Item Coverage`, `Context`, `Open Questions`, `Assumptions`,
`Done When`, `Changes`, `Size and Coherence`, `Tests`, `Validation`,
`Risks and Edge Cases`, `Revisions`.

```markdown
## Done When

- S3-D1: `waif check` reports a gap in review numbering.

## Changes

- S3-C1: Detect gaps while listing review files in `src/protocol/task.rs`.
```

`Done When` holds the step's done conditions: `S3-D1` is the condition the
current protocol numbers `S3-DC1`. Each `Changes` item is a key decision
`S<n>-K<m>` with the same number, and its paths are the step's changed
files. References to `S3-D1` or `S3-C1` elsewhere in the task mean those
items; implementation and final reviews keep their original references.

## Questions and assumptions

A goal, plan, or step listed unresolved major issues in `Open Questions`, and
minor issues resolved by a best-effort choice in `Assumptions`. Both used
compact items, often with nested-list details:

```markdown
## Open Questions

- P-Q1: Branch naming for linked worktrees
  - Detail: Linked worktrees need a branch, and the plan does not name one.
  - Risk: A wrong name breaks plan acceptance in linked worktrees.
  - Options:
    1. Reuse the task branch name.
    2. Add a worktree suffix.

## Assumptions

- P-A1: Default timeout unit
  - Detail: The goal gives timeouts without a unit.
  - Assumption: Timeouts are in seconds.
  - Risk: Configuration in milliseconds times out 1000 times later.
```

`Open Questions` is the section the current protocol names `Questions`.
Every question in it is `open`: a resolved question was removed. The parent
line is the item title, `Detail` and `Options` keep their meaning, and a
question's `Risk` is its `Impact`. An assumption's `Assumption` is its
`Choice`; `Detail` and `Risk` keep their meaning. Fields the old form lacks,
such as `Affects` and `Recommendation`, stay unknown until the agent works
them out.
